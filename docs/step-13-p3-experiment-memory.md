# Step 13：P3 实验台账与经验回灌 —— 发布即登记、到期判定、经验回到决策

## 1. 这一步做了什么

把"发布完了"变成一件有时序的事：

```text
publish 成功
   └─ 登记 experiments.jsonl（基线 = 发布前 28 天，窗口 = 任务单给的 14/21 天）
        └─ 窗口到期 → 代码判定（成立 / 不成立 / 不确定 / 样本不足）
             └─ 模型把已判定的实验归纳成 lessons.json
                  └─ 下一轮主管决策时，experiments + lessons 一起注入
```

新增两个模块、三个命令、一个运营台区块：

| 位置 | 作用 |
|---|---|
| `src/ops_agent/experiment.py` | 登记、日序列适配、两比例检验、四态判定、样本量估算 |
| `src/ops_agent/lessons.py` | 经验归纳的提示词、校验、数字溯源 |
| `publish` | 发布成功回调 `on_published`，失败不影响已完成的发布 |
| `experiment register / judge / list` | 手工补登、到期判定、台账查看 |
| 运营台 | 新增"实验台账"面板，表格 + 经验列表 |

## 2. 分工：算术归代码，解释归模型

这是 P3 唯一一条不可让步的边界。

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 基线、窗口、累计转化率 | 代码 | 加总与除法没有解释空间，错了就是错了 |
| 显著性（两比例 z 检验） | 代码 | 同上；`math.erfc` 一个公式，不引 scipy |
| 三态结论 | 代码 | FR-508 要求"样本不足不得给成立"，这条必须硬 |
| "这说明什么、下次怎么做" | 模型 | 跨实验的归纳是模型擅长的，且错了代价可控（经验可被下一轮验证） |

所以 `judge()` 里没有一次模型调用：`experiment judge --no-lessons` 跑得飞快，主管每周开头也能零成本判定所有到期实验。

## 3. 登记

### 3.1 发布即登记

`publish()` 成功分支调用注入的 `on_published(proposal, preview)`，返回 `experiment_id` 写进 `PublishResult`。三个细节：

- **只在成功分支调用。** 被合规拦截、令牌无效、锁冲突、写入失败的路径都不会产生实验。
- **回调异常不回滚发布。** 文案已经上线，因为台账写不进去而回滚是更坏的选择；异常转成 `PublishResult.warnings`，CLI 打印 `[WARN] … 实验登记失败`。
- **幂等。** `append_experiment` 按 `experiment_id` 去重，同一版本同一天重复发布不会产生第二条。

`experiment_id = product_id + variant_id + 开始日期`（PRD 9.4），例如 `SKU-1001:SKU-1001-v1:2026-10-10`。

### 3.2 基线只算一次

`baseline_for()` 把发布前 28 天的曝光/点击/订单**先加总再相除**，得到与观察窗口同构的比率。日均比率的算术平均会让冷清的一天和爆量的一天等权，这是错的。

基线在登记时写进 `baseline` 字段并冻结，之后判定只读它 —— 否则商品数据一变，历史结论就跟着变，无法回放。

### 3.3 数据从哪来

| 场景 | 基线来源 | 日序列来源 |
|---|---|---|
| CLI 离线 | 本地 `performance.csv` 前 28 天 | 同左 |
| CLI 连站点 | 商品 30 天 `metrics`，标 `source=site_metrics` | 站点未提供按日接口 → 判定为样本不足 |
| 运营台 | 租户快照里的 `metrics`，标 `source=site_snapshot` | 同上 |

站点商品 id 与本地日序列表的主键不是一回事，所以记录里单独存 `series_key`：补登时可以用 `--series-key SKU-1001` 明确指定"用哪条序列判定"，而不是靠猜。

## 4. 判定

### 4.1 状态机

```text
observing ──窗口未满──> observing（只报进度，不给结论）
    │
    └──窗口到期──> verdict
                     ├─ insufficient  天数<7 或 曝光<300 或 点击<30 或无基线
                     ├─ supported     提升≥min_lift 且 p<0.05
                     ├─ rejected      提升≤0 且 p<0.05
                     └─ inconclusive  其余（含"达目标但不显著"）
```

基线订单为 0 时相对提升无定义，改按"窗口内是否显著出单"判定，并在 `note` 写明"基线无订单"。这不是放宽标准，是承认除零没有业务含义。

### 4.2 把"不显著"翻译成"还差多少"

只写"p=0.92，不显著"，运营看不出是"没效果"还是"数据不够"。所以每条结论都带 `required_impressions`：按当前基线转化率与 `min_lift`，用 α=0.05、power=0.8 反算每组需要多少曝光。

真实数字（本轮实测）：

| 判据 | 基线 | 目标提升 | 每组所需曝光 |
|---|---|---|---|
| 订单率 | 0.24% | +15% | **311,695** |
| 点击率 | 5.0% | +15% | **14,193** |

单个商品 14 天曝光约 1.3 万。**用订单率做判据，14 天窗口差 24 倍；换成点击率，刚好够。**

这是 PRD Q4"14 天是否合适"的量化回答：窗口不是问题，**判据选什么才是问题**。下一步该让主管在派单时优先选点击率/询盘率这类高基数指标，把订单率留给 28 天终判。

## 5. 经验库

### 5.1 输入只有已判定的实验

`derive_lessons()` 拿到的是 `verdict` 非空的记录：假设、角度、基线 vs 实测、lift、p、结论。窗口内的实验不进归纳 —— "还在跑"不能变成经验。

### 5.2 三道校验

| 校验 | 做法 | 挡住什么 |
|---|---|---|
| 数字必须来自证据 | 条目里的百分数必须在 lift / 基线 / 实测 / 目标里找得到（容差 0.05 个百分点） | "订单率提升 40%"这种编造 |
| 单条证据不给高置信 | `evidence_count ≤ 1` 时 `confidence` 强制 ≤ 0.4 | 一次侥幸被当成规律 |
| 空结果不覆盖 | 模型返回空或全部被丢弃时保留原 `lessons.json` | 把积累的经验清零 |

去重按 `(scope, statement)` 小写比较；同一批里重复的只留第一条。

### 5.3 模型不可用

直接 `LessonError`，CLI 打印"经验库未更新"并返回 1。不产出规则兜底的经验 —— 与 FR-510 一致：宁可这周没学到东西，也不写一条编的。

### 5.4 探针：真实模型 + 三条有明确结论的实验

`scripts/p3_lesson_probe.py` 给模型三条合成实验（两条成立、一条不成立，数据不写台账），验证它会不会写出站得住的经验：

```text
[worked] home-kitchen   将盖型差异同时写入标题与订单文件，可减少错发并使订单率提升 34.0%。（证据 1 · 置信 0.4）
[worked] copy:lead-time 在标题中前置交付周期与起订量，可使点击率提升 22.0%。（证据 1 · 置信 0.4）
[failed] home-kitchen   不要只降价而不改文案，单纯降价 8% 反而使订单率下降 12.0%。（证据 1 · 置信 0.4）
```

三条都带数字，四个数字（34% / 22% / 8% / 12%）全部能在证据里找到；`scope` 是短标签（类目或 `copy:*`）而不是整句角度；单条证据的置信被压在 0.4。

这个探针抓出过两个真实的误杀，见第 8 节最后两行。

## 6. 回到决策

主管本来就通过 `memory.context()` 拿 `store_profile / experiments / decisions / lessons`，P3 没有新增注入通道，只是让这三个文件第一次有内容。每轮开始时 `memory.snapshot(run_id)` 把这四类整体冻结，事后能查"当时模型看到了什么"。

周循环闭合在 `director run` 开头：先 `_judge_due_experiments()`（纯代码、零成本）判定所有到期实验，打印"到期实验: 判定 N 条（成立 x · 不成立 y）"，再进模型决策。经验回灌仍是显式的 `experiment judge`，不隐式花钱。

## 7. 真实运行

补登三条历史实验（本地序列，`--started-at 2026-10-10`，窗口 14 天，目标 +15%）：

```text
商品       版本          结论    提升     曝光    依据
SKU-1001   SKU-1001-v1   不确定  +2.8%   13397   提升未达目标（提升 2.8%，p=0.923）；当前曝光 13,397，要判定需约 321,914
SKU-1003   SKU-1003-v1   不确定  -2.4%   10285   提升未达目标（提升 -2.4%，p=0.955）；当前曝光 10,285，要判定需约 537,216
SKU-1007   SKU-1007-v1   不确定  -14.5%   7910   提升未达目标（提升 -14.5%，p=0.772）；当前曝光 7,910，要判定需约 633,714

判定 3 条 · 成立 0 · 不成立 0 · 不确定 3 · 样本不足 0
```

三条全部"不确定"是**正确结果**，不是失败：模拟店铺的订单率约 0.24%，单商品 14 天一万多曝光，统计上根本分不出 15% 的提升。三条的所需曝光都落在 32 万–63 万，是当前曝光的 24–80 倍。

经验归纳（MiniMax-M2.7-highspeed，1 次调用 1,571 token，7 秒）：

```json
{
  "scope": "store",
  "statement": "曝光量未达到判定要求时应延长实验并继续收集数据，不要据此做出推广或停止决策。",
  "direction": "mixed",
  "evidence_count": 3,
  "confidence": 0.4
}
```

模型没有硬凑"标题改写有效"这类结论，而是归纳出"数据不够别下结论"，并把置信压到 0.4 —— 这正是希望它学会的东西。

主管读取验证：`director run` 1 次调用 18,981 token，快照 `memory/snapshots/20261103-112312-3fee.json` 里 `lessons` 1 条、`experiments` 3 条，确认下一轮决策能看到。

## 8. 痛点与解决

| 痛点 | 现象 | 解决 |
|---|---|---|
| 结论比数据早到 | 窗口没满就想给"成立" | 未到期一律 `observing`，只报进度；`judge()` 里没有提前返回结论的分支 |
| 基线被事后改写 | 商品数据更新后，历史结论跟着变 | 基线登记时冻结，判定只读 `record["baseline"]` |
| 除零崩溃 | 基线 0 订单时 `lift` 无定义 | 改判"是否显著出单"，note 说明基线为零 |
| "不显著"被读成"没效果" | 运营看到 p=0.92 就放弃 | 每条结论带 `required_impressions`，直接给出还差多少曝光 |
| 台账写失败连累发布 | 文案已上线，回调异常 | 异常转 `warnings`，发布保持 `published`；测试 `test_hook_failure_keeps_the_publish` |
| 经验写成小说 | 模型爱总结"XX 有效" | 数字溯源 + 单证据限置信 + 空结果不覆盖 |
| 站点没有按日数据 | 真实商品判定不了 | 判 `insufficient` 并写明"数据源未覆盖该商品"，不拿 30 天滚动值硬凑 |
| `scope` 写成整句 | 第一版探针返回 `scope="把盖型差异写进标题与订单文件"`，经验无法按类目或手段检索 | 提示词把 `scope` 限定为「类目 slug / `copy:<lever>` / `store`」，明令不得粘贴角度原文 |
| 数字溯源误杀（负值） | `lift=-0.12` 存的是 -12.0，模型写"下降 12%"，比较时正负不等被丢弃 | 允许集合统一取绝对值，方向由 `direction` 表达 |
| 数字溯源误杀（来源） | "单纯降价 8%" 的 8% 来自提案角度而不是 outcome，被当成幻觉丢弃 | 允许集合纳入 `angle / hypothesis / problem / success_metric` 里的百分数，它们本来就是输入证据 |

## 9. 测试

```bash
python -m unittest discover -s tests
# Ran 402 tests · OK（P2 356 + P3 新增 46）
```

P3 专项：

- 窗口：未满只报进度、到期四态、窗口外数据不计入、`started_at` 坏值不崩。
- 统计：显著提升成立、显著下降不成立、小幅下降不确定、基线为零的两种走向、缺基线判样本不足。
- 样本量：0.24% 需要 20 万+，5% 只需 3 万以内；结论里带 `required_impressions`。
- 幂等与回放：`experiment_id` 格式、重复登记跳过、`apply_judgement` 保留原字段。
- 经验：编造百分数被丢弃、有依据的保留、负 lift 与角度里的百分数不被误杀、单证据限 0.4、重复合并、超长截断、模型不可用报错、空结果保留旧库。
- 发布钩子：成功才触发、拦截不触发、回调失败不影响发布。
- 周循环：主管判定到期实验、未到期不动、已判定不重算、`rejudge` 可重算。

## 10. 已知边界

- **真实发布未执行。** 发布即登记需要一次性审批令牌并写入线上站点，本轮只用 3 个单元测试覆盖三条路径；真实发布要人工签发令牌后才会产生第一条真实实验。
- **站点无按日指标。** Agent API v1.1 只给 30 天滚动聚合，真实商品无法做窗口判定。这是外部依赖，需要站点补一个按日端点。
- **判定指标受任务单影响。** 任务单的 `success_metric` 是自由文本（如 `order_rate_pct从当前0.07%提升至至少0.0875%`），代码靠关键词解析；解析不到时回落到 `order_rate` 并在 `metric_note` 标注。
- **询盘率用点击率代理。** 本地序列没有 inquiries，`inquiry_rate` 会退化为 `click_rate` 并写明代理关系。
- **经验库没有版本历史。** `lessons.json` 覆盖写，只保留当前快照；需要对比历次经验时依赖 `memory/snapshots/*.json`。
- **实验台账未做归档。** PRD 说保留 52 周，目前只追加不清理。
