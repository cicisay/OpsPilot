# Step 14 / P4 — 运营台深化：体检、实验看板、记忆浏览

> 目标：把 P1–P3 产出的数据变成运营人员能在一屏内读懂的东西，并把"哪些版本能批"从口头约定变成界面与接口的双重约束。
> 范围：`src/ops_agent/console/`（新增 `insight.py`、`app.py` / `server.py` 接入、前端三个文件重做）。

## 1. 做了什么

### 1.1 新增视图层 `console/insight.py`

运营台原本在 `overview()` 里直接拼 JSON。P4 要四类面板、六项指标、跨文件 join，继续堆在一个方法里会变成无法测试的 200 行。于是把"文件 → 面板数据"抽成纯函数模块，只读、不改、缺文件不抛异常。

| 函数 | 产出 | 关键点 |
|---|---|---|
| `build_checkup(dir)` | 健康度、异常类目分布、选品数量与理由 | 类目分布按**本周选中**聚合，弱类目即使没选中也列出 |
| `build_experiment_board(dir, today)` | 观察中 / 已判定两组 | `days_left` **实时重算**，不复用判定时存下的值 |
| `build_memory(dir)` | 画像、决策、经验、快照索引、完整性 | 只读，坏行计数一并给出 |
| `replay_snapshot(dir, run_id)` | 某一轮实际注入的记忆原文 | `run_id` 做白名单校验，非法即拒 |
| `build_metrics(dir, today, trace_dir)` | PRD 12.1 的六项指标 | 每项带阈值与告警判定 |
| `attach_verdicts(proposals, reviews)` | 把四类结论挂到每个版本 | 同时索引 `variant_key` 与 `variant_id` |

### 1.2 面板

**店铺体检**：左侧健康度分数（≥70 绿 / ≥50 黄 / 其余红），中间体检结论 + "最该动的" + 本周选品数与区间 + 版本数理由折叠，右侧异常类目分布（弱类目标黄，本周动过的显示数量与主要问题）。

**本周动作**：表格改卡片。每张卡有标题、自创问题类型、来源徽章、分数，2×2 网格放假设 / 成功判据（含目标提升与窗口）/ 价格带（含价位点）/ 版数（含模型给的理由），证据默认折叠。

**方案与审批**：见 1.3。

**实验看板**：顶部五个计数（观察中 / 成立 / 不成立 / 不确定 / 样本不足），观察中表格给判据、基线 → 当前、剩余天数、进度条（优先按曝光进度，没有所需曝光时退回窗口进度），已判定表格给结论、基线 → 当前、提升、完整依据。

**记忆**：四个 tab（画像 / 决策 / 经验库 / 快照回放）。快照点"回放"调 `GET /api/tenants/{tid}/memory/{run_id}`，展开后是当轮主管真正拿到的画像、决策、实验与经验原文 —— 这是 FR-804 的界面落点。

### 1.3 合规四类矩阵与不可批

每个版本显示四格（绝对化 / 知识产权 / 类目资质 / 目标市场），不允许用"合规通过"一个绿标盖住某格 warn。命中代码硬禁时额外一行红字"代码覆盖：模型判通过，硬禁改判否决"。违规项带原文引文、规则说明与改法。

版本切换按钮上带状态点；block 版本整颗按钮转浅红。**签发与发布按钮在 block 或未审时直接 disabled，并写明原因。**

## 2. 四个设计决定

### 2.1 合规并入方案详情，不设独立页

PRD 12.2 把"合规"列成独立页面。单页架构下照做会带来两份数据：列表里的严重度和详情里的矩阵一旦刷新不同步，运营会看到互相矛盾的结论。

改为：方案卡显示汇总（`合规 3/3`、`合规 提示 3`、`合规 否决 1`），详情显示矩阵。一处数据，两个粒度。PRD 要求的"四类矩阵 + block 不可批"两项都满足。

### 2.2 未审版本也不能批

原来只有 `severity == block` 拦截。但"没人审过"和"审过没问题"是两件事，前者更危险 —— 它意味着合规 Agent 没跑过或者版本是手工塞进来的。

`approve` 改成两段判断：没有结论 → 409「该版本还没有合规结论，先运行 review 再审批」；有结论且 block → 409「已被合规否决」。发布侧不动（`publish` 只拦显式 block），因为能签发令牌的必然已有结论，链路是闭合的。

这条改动让一个既有测试失效（它用虚构的 `p1/v1` 签发令牌），已改为显式注入 verdict 并新增两条反向用例。

### 2.3 指标里的"平均调用数"只算两个按商品伸缩的 Agent

主管每批只调 1 次，工坊与合规按商品数伸缩。第一版把 trace 里所有调用除以商品数，结果最新一轮恰好只跑了主管，指标显示 0.25 —— 数字没错，含义错了。

改为只统计 `workshop` + `compliance`；一次都没有时显示 `—` 并写明"最近一轮没有工坊或合规调用"，不显示 0 假装健康。

### 2.4 剩余天数重算，不信任存储值

`experiment.judge()` 会把 `days_left` 写进 `outcome.window`，那是判定当时的值。看板如果直接展示，一条 10 天前判定"还有 3 天"的实验会永远显示 3 天。

`build_experiment_board` 用 `started_at + window_days - today` 重算，并单独给 `overdue` 标记。

## 6. 边界

- **指标是单租户视角，调用数是整机视角**。trace 按 run 落盘、不含租户字段，所以"平均调用数"标注为"最近一轮"，不与租户数字混算。多店铺并行时这个数会互相干扰。
- **"完成率"的分母取任务单 `variant_max` 之和**。工坊少出几版（在区间内合法）会让完成率低于 100%，这是有意的：计划与交付的差就是要被看见。
- **快照只保留 run_id 可枚举的那些**。回放不到没有快照的历史轮次（P3 之前的数据）。
- **合规没有独立页**，理由见 2.1。
- **实验看板不做交互式筛选**，只有观察中/已判定两段。超过 30 条各截断，按到期时间排序。
- `scripts/p4_shot.js` 与 `scripts/p4_gate_check.js` 依赖本机 Edge，属于验证脚本，不在测试套件内。
