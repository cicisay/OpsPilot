# Step 3 — 运营主管 Agent：体检、选品、诊断、TaskOrder

## 本步目标

把真实店铺的数据变成“本周该动哪 5 个 SKU、为什么、怎么改、怎么算成功”。先用确定性规则跑通，再把规则换成 LLM planner；输出结构不变。

## 交付物

| 文件 | 作用 |
|---|---|
| `src/ops_agent/supervisor.py` | 类目中位数基准、诊断规则、价格带、WeeklyPlan |
| `src/ops_agent/cli.py` | 新增 `supervisor run`（实时 / 离线） |
| `tests/test_supervisor.py` | 12 个诊断与计划测试 |
| `data/task_orders.json` | 真实店铺生成的 TaskOrder |

## 输入输出

输入：

- `SiteProduct[]`：商品、变体、价格、成本、库存
- `SiteMetrics`：PV、UV、询盘、订单、件数、收入、评价、差评
- 时间窗 `days`（默认 30）

输出 `WeeklyPlan`：

- 扫描数、命中数、选中的 5 个
- 每个 SKU：问题、分数、证据、假设、动作、成功指标、价格带、毛利底线、预算

## 关键决策

1. **规则先行，LLM 后接。**
   规则能跑通、能解释、能回归；LLM 只负责“在规则之上选得更细”。TaskOrder 的字段先定死，后面换 planner 不动结构。
2. **基准用类目中位数。**
   平均数会被一个爆款拉高；中位数更稳。类目样本少于 3 个时退回全局中位数，避免小样本失真。
3. **指标换成 B2B 口径。**
   站点没有曝光/CTR：用 `PV`、`询盘率 = 询盘 / PV`、`下单率 = 订单 / PV`、`毛利率`、`库存天数`。
4. **诊断有优先级。**
   差评 > 下单低 > 询盘低 > 流量低 > 库存风险 > 库存积压 > 毛利低；分数 = 严重度 × 流量权重。
5. **库存积压只在流量正常时成立。**
   低流量 + 高库存，根因是流量，不是库存；先治流量，否则会把“没人看”误诊成“货太多”。
6. **价格带 ±10%，但不破毛利底线。**
   下限取 `max(当前价 × 0.9, 成本 / (1 - 16%))`；低毛利场景下限不低于当前价。
7. **同类问题最多 2 个。**
   第一轮每类最多 2 个，保证本周动作有区分度；不够再按分数补齐。

## 难点与解决

**难点 1：真实数据很稀疏。**
30 个商品里不少是 0 询盘、0 订单，率值会变成 0。直接和 0 比会全员异常。解决：用类目中位数做基准，并设“PV ≥ 中位数 65%”才判断询盘/下单，避免小流量样本噪声。

**难点 2：低流量和库存积压同时出现。**
第一版把“库存 900 天”判成积压，但那个商品 PV 只有 400，真正的问题是没人看。解决：积压规则加 `PV ≥ 中位数 65%`，低流量优先治流量。

**难点 3：价格带既要能测试，又不能亏。**
单纯 ±10% 可能跌破成本线。解决：下限和 `成本/(1-16%)` 取大；低毛利场景下限不低于当前价，先提价再谈成本。

**难点 4：线上和离线结果要一致。**
如果实时和快照用两套逻辑，演示和复盘会对不上。解决：同一个 `build_plan`，输入都是 `SiteProduct[]`；`load_snapshot` 只负责把 JSON 还原成模型。

**难点 5：测试基准会被异常样本污染。**
6 个异常样本 + 3 个正常样本，中位数会被拉到异常一侧，导致“全员正常”。解决：测试用 9 个基准 + 6 个异常；真实逻辑里类目样本不足 3 个时退回全局中位数。

## Bug 记录

**Bug 1：低流量被误诊为库存积压。**
`stock > 120` 只看了库存天数，没有排除低流量，结果“PV 400、库存 900 天”被判成积压。修复：加 `pv >= 中位数 × 0.65` 条件，低流量优先。

**Bug 2：计划输出把“命中数”写成了“选中数”。**
页面显示“命中 5 个”，但实际命中 21 个、只选 5 个。修复：`WeeklyPlan` 增加 `matched` 字段，CLI 分开打印。

**Bug 3：离线测试写系统临时目录被沙箱拒。**
`tempfile.TemporaryDirectory()` 在 `<TEMP>` 下被 DSH 沙箱拒绝。修复：测试改用 `unittest.mock.patch("pathlib.Path.read_text")`，不写磁盘。

## 设计问答

**Q1：为什么先用规则，不直接上 LLM？**
A：规则能解释、能回归、能定位问题。LLM 在“多个都异常时选哪个、怎么措辞”上有价值，但基准、优先级、价格底线不能交给它。先用规则把结构和数据跑通，再让 LLM 在规则内做选择。

**Q2：为什么基准用中位数，不用平均数？**
A：30 个商品里只要有一个爆款，平均数就会被拉高，其他商品全变“低流量”。中位数对极端值不敏感；类目样本少于 3 个时用全局中位数，避免小样本。

**Q3：低流量和高库存同时出现，先治哪个？**
A：先治流量。库存是结果，不是原因；如果 PV 只有 400、库存 900 天，正确动作是改标题/关键词，而不是清仓。代码里积压规则要求 PV 不低于中位数 65%。

**Q4：价格带怎么定，怎么保证不亏？**
A：先取当前价 ±10%，再用 `成本/(1-16%)` 抬下限；低毛利场景下限不低于当前价。这样既能做实验，又不会跌破毛利底线。

**Q5：怎么保证线上和离线结果一致？**
A：同一个 `build_plan`，输入都是 `SiteProduct[]`；实时走 `SitePlatform`，离线走 `load_snapshot`，两者只在“数据来源”不同。测试和联调都验证过结果一致。

**Q6：这套诊断怎么接后面的内容工坊和合规？**
A：TaskOrder 里已经有 `action`、`hypothesis`、`success_metric`、`price_band_cents`，内容工坊只要按 TaskOrder 生成 2–3 版方案；合规按现有四类规则审；发布走连接器的 dry-run + 幂等写入。

## 已知限制

1. 真实店铺只有 30 个商品，类目样本偏少；样本多了以后中位数基准会更稳。
2. 诊断只看 30 天窗口，没有趋势（环比/同比）；下一步可以加趋势特征。
3. 规则没有考虑季节、广告、竞品；这些留给 LLM planner 或后续数据接入。
4. 单店铺部署；多店铺要按 storeId 隔离基准和任务单。
