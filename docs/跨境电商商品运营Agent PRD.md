# 文档摘要

这份 PRD 定义一个面向跨境店铺的商品运营 Agent。它不解决“帮我写一段文案”，而是解决“这周该动哪个 SKU、改什么、改完有没有用、下次能不能复用”。

表 0-2 一页纸摘要

| 维度 | 结论 |
| --- | --- |
| 问题 | 商品运营高频、琐碎、靠人盯；文案工具只解决“写”，不解决“改完有没有用”。 |
| 方案 | 三个 Agent 协作：运营主管做决策，内容工坊做生成，合规审查可否决。 |
| 差异 | 每个改动都有假设、预期、结果、结论；发布可回放；经验沉淀为 Playbook。 |
| 边界 | 只用自家、官方、公开三类数据；不爬竞品；发布与人审绑定；不承诺 GMV。 |
| 指标 | 单 SKU 周环比 CTR/CVR（对对照组）、上架时长、实验胜率、合规拦截准确率、Playbook 复用率。 |

> **一句话**给跨境店铺一个会自己找活、会试错、会记教训的运营助理，而不是一个更快的文案生成器。

# 1. 背景与问题

## 1.1 业务背景

跨境店铺的商品运营是典型的高频、琐碎、靠人盯的工作：发品要写多语种标题、卖点与描述；选品要看趋势、价格带与利润；素材要做图、拍视频；上架之后还要盯曝光、点击、转化、退货。一个运营同时管几十个 SKU，只能按经验排序；改完之后，也很难判断到底是改动起了作用，还是季节和流量波动的巧合。

更麻烦的是经验留不下来。哪个类目换场景主图有效、哪个市场必须补尺寸表、哪类词会触发平台审核——这些结论散落在个人笔记和聊天记录里，换一个人就从零开始。

## 1.2 现有工具的四个缺口

- **只写不改：**文案工具解决“生成”，不解决“发布后有没有用”。
- **只报不判：**数据工具给报表，但不告诉你下一步改什么、改完怎么验证。
- **无法归因：**人工一次改三处，涨了不知道是谁的功劳，跌了也不知道该退回哪一处。
- **合规靠运气：**竞品抓取、绝对化用语、图片版权，往往上线后才发现。

## 1.3 机会

平台官方数据接口、生成模型、单变量实验、长期记忆，这四件事同时具备，才可能把“优化”从手工艺变成可复用的闭环：有数据能诊断，有模型能生成，有实验能归因，有记忆能复用。

## 1.4 本产品不做什么

- 不做全自动铺货、刷单、跟卖。
- 不替代店主做定价与选品的最终决定。
- 不抓取竞品页面、评论与图片。
- 不承诺 GMV，只承诺决策质量、效率与可审计。

# 2. 产品定位与目标

## 2.1 一句话定位

> **定位**给跨境店铺一个会自己找活、会试错、会记教训的运营助理：每周自己体检、选 SKU、诊断、出方案、过合规、发布、看结果、记结论。

## 2.2 目标用户

表 2-1 目标用户

| 角色 | 关心什么 | 当前痛点 | 在本产品里的动作 |
| --- | --- | --- | --- |
| 店主 / 操盘手 | 毛利、周转、风险 | 不知道钱花在哪、改动有没有用 | 看周报、批超阈值动作 |
| 运营专员 | 先干什么、有没有依据 | 凭感觉排序，改完说不清原因 | 看诊断、确认方案、复盘 |
| 美工 / 内容 | 出图出文案的效率与规范 | 反复改稿，需求描述不清 | 接收 brief、复用素材 |
| 合规 / 风控 | 不踩平台与广告法红线 | 事后才发现，整改成本高 | 维护词库、抽检、处置驳回 |

## 2.3 产品目标

- **G1 决策闭环：**每个改动都有假设、预期、结果、结论；没有结论的实验不算完成。
- **G2 可审计：**每次发布可回放到证据、审批人、版本；谁改的、为什么改、什么时候改，都能查。
- **G3 记忆复用：**同类 SKU、同类市场的有效做法沉淀为 Playbook，换 SKU 直接复用。

## 2.4 非目标

不做多平台统一投放，不做供应链与物流，不做站外广告代投。这些是下一阶段或合作方的事，不在本期范围。

## 2.5 成功指标

表 2-2 成功指标

| 类型 | 指标 | 定义 | 目标 |
| --- | --- | --- | --- |
| 北极星 | 单 SKU 周环比 CTR / CVR | 相对对照组的变化 | CTR ≥ +15%，CVR ≥ +10% |
| 效率 | 上架时长 | 资料齐备到上线 | ≤ 2 小时 / SKU |
| 质量 | 合规拦截准确率 | 精确率 / 召回率 | ≥ 90% / 抽检 100% |
| 复用 | Playbook 复用率 | 被复用的结论占比 | ≥ 60% |
| 成本 | 单 SKU 单周成本 | 模型 + 素材 + 人工 | 预算内，周报可见 |

# 3. 用户与场景

## 3.1 三个用户故事

陈姐，店主，管 3 个店、120 个 SKU。她每周只看一次报表，最怕“钱花了不知道有没有用”。她要的周报是：这周动了 5 个，3 个有效，2 个回滚，下周建议动哪 3 个。

阿岚，运营，每天被问“为什么改这个”。她需要每个改动都有假设、预期和数据依据，而不是“我觉得主图不好看”。

老周，合规，最怕上线后才发现违规。他要的是发布前拦住，并且明确告诉他是哪条规则、改哪一句能过。

## 3.2 一周节奏

表 3-1 一周节奏

| 时间 | 角色 | 动作 | 产出 |
| --- | --- | --- | --- |
| 周一上午 | 运营主管 | 拉数据、体检、选 SKU、诊断 | 任务单 3–5 个 |
| 周一下午 | 内容工坊 | 并行出 2–3 版文案 / 素材 / 价格 | 候选方案包 |
| 周二上午 | 合规审查 | 四类检查，驳回或放行 | 审查结论 |
| 周二下午 | 运营主管 + 人工 | 选版；超阈值审批 | 发布指令 |
| 周二晚 | 发布器 | 上线、版本化 | listing 版本号 |
| 周三–周日 | 系统 | 观察窗、样本累积 | 表现数据 |
| 下周一 | 运营主管 | 对比对照组、判定、写记忆 | 周报 + Playbook |

## 3.3 核心场景

**S1 诊断优化：**CTR 低于类目基线 20% → 诊断 → 换场景主图 → 合规 → 发布 → 观察 7 天 → 保留或回滚，结论入库。

**S2 新品发品：**产品资料齐备 → 生成多语种 Listing 与素材 → 合规 → 发布，目标 2 小时内上线。

**S3 合规驳回：**品牌词、绝对化用语、图片版权 → 驳回并给出违规项 → 修改 → 复审，最多 2 轮。

**S4 周复盘：**周一对对照组判定 → 写 Playbook → 生成周报与下周计划。

# 5. 三 Agent 协作设计

## 5.1 设计原则

- **按立场拆，不按步骤拆：**三个角色分别代表增长、表达、风险；按“诊断→生成→发布”拆只是流水线换名字。
- **上下文隔离：**合规只拿成品和规则，不看创作理由；否则它会被说服。
- **schema 交接：**Agent 之间传 Pydantic 对象，不传自然语言，避免错误被放大。
- **否决单向：**合规能否决，主管只能升级人工，不能推翻。
- **单写者：**记忆只由运营主管写，避免三个 Agent 各记一份、互相矛盾。

## 5.2 角色清单

表 5-1 三角色清单

| Agent | 职责 | 输入 → 输出 | 工具 | 权限边界 |
| --- | --- | --- | --- | --- |
| 运营主管 | 体检、选 SKU、诊断、定假设与价格带、派活、实验判定、写记忆 | 全店数据 + 历史实验 → 任务单 / 发布指令 / 周报 | 快照、趋势、评论、统计、发布、回滚 | 唯一可发布 / 回滚；不能推翻合规 |
| 内容工坊 | 按任务单出 2–3 版文案、素材与价格方案 | 任务单 + 品牌规范 → 候选方案包 | 文案、素材、价格计算 | 只写草稿；不能发布、不能越价格带 |
| 合规审查 | 禁售、广告法、品牌词、版权四类检查，可否决 | 候选方案 + 规则库 → 通过 / 不通过 + 违规项 | 词库、版权检查 | 否决权；不能改内容、不能发布 |

**失败模式：**主管容易过度优化、被短期波动骗；工坊容易模板化、夸张承诺；合规容易误报过多拖慢效率。对应防线见 5.7 与第 10 章。

## 5.3 从 6 个角色收敛到 3 个

表 5-2 角色合并映射

| 原角色 | 并入 | 理由 |
| --- | --- | --- |
| 运营主管 | 运营主管 | 保留，成为唯一决策者与唯一写记忆者 |
| 诊断师 | 运营主管 | 诊断是决策的一部分，拆开要来回传上下文 |
| 创作 | 内容工坊 | 保留 |
| 定价 | 主管定边界 + 工坊出方案 | 毛利 vs 转化由主管定线，方案由工坊在带内优化 |
| 合规官 | 合规审查 | 保留，独立性不能并 |
| 实验分析 | 运营主管 | 判定是决策闭环的最后一环，和派活同源 |

## 5.4 协作流程

1. 周一 09:00，主管拉取店铺快照，按健康度选 3–5 个 SKU。
2. 主管诊断，生成假设与成功标准，定价格带与毛利底线，下发 TaskOrder。
3. 工坊并行生成 2–3 版 Proposal，每版带假设、预期与素材。
4. 合规逐版审查，输出 ReviewResult；不通过则带违规项退回。
5. 工坊修改，最多 2 轮；超过 2 轮转人工，避免死循环。
6. 主管选版；降价超过 10%、改类目、动品牌词等超阈值动作转人工审批。
7. 主管发布并版本化，进入 7 天观察窗（或累计 1000 曝光）。
8. 下周一对比对照组，判定保留 / 回滚 / 加推，写实验记忆，生成周报。

## 5.5 交接协议

表 5-3 交接对象

| 对象 | 关键字段 | 流向 |
| --- | --- | --- |
| TaskOrder | sku_id、market、problem、hypothesis、price_band、margin_floor、success_metric、budget_tokens | 主管 → 工坊 |
| Proposal | variants[]（每版含文案 / 素材 / 价格）、expected_lift、rationale | 工坊 → 合规 / 主管 |
| ReviewResult | verdict、violations[]、suggestions[] | 合规 → 主管 |
| PublishCommand | sku_id、variant_id、approval_token | 主管 → 发布器 |

## 5.6 冲突与仲裁

表 5-4 冲突与仲裁

| 冲突 | 仲裁 | 兜底 |
| --- | --- | --- |
| 创作想夸张，合规要拦 | 合规优先 | 人工可推翻合规，但必须留痕并记录理由 |
| 定价想降，毛利线不允许 | 主管定价格带 | 低于毛利线自动转人工 |
| 主管想连续改动 | 最小观察窗 + 频率上限 | 预算耗尽即停止 |
| 多 SKU 抢发布窗口 | 主管排序 | 人工调整优先级 |

## 5.7 四条硬规则

- **修改最多 2 轮：**超过转人工，防止工坊与合规死循环。
- **记忆单写者：**只有主管写记忆，其他角色只读。
- **否决单向：**合规能否决，主管不能推翻，只能升级人工。
- **发布令牌：**只发给主管，一次一用，后端校验。

## 5.8 为什么是三个

再砍一个只有两种砍法：把合规并进主管，独立否决就没了——主管既想增长又审自己，等于没有审查；把工坊并进主管，创作和决策混在一起，出了问题分不清是“判断错”还是“写错”，也没法并行出多版。三个是保住制衡的最小数量。

## 6.1 FR-01 体检与选品（P0）

**描述：**按曝光、CTR、CVR、退货、库存五个维度给每个 SKU 打分，输出本周建议优化的 3–5 个，并说明理由。

**输入：**店铺快照（≥14 天）、库存、毛利。

**输出：**候选清单、分数、理由、预估收益。

**规则：**优先“高流量低转化”，其次“高退货”，最后“低曝光”；库存风险单独标记，不混入优化队列。

**验收：**运营人工评审 20 次，≥80% 认可排序；漏掉明显问题 SKU 的次数为 0。

## 6.2 FR-02 诊断与假设（P0）

**描述：**按决策表定位问题，生成 2–3 个假设，每个假设带预期指标与成功标准。

**输入：**SKU 数据、类目基线、自家评论与退货原因。

**输出：**诊断结论、假设列表、所需证据。

**规则：**一次只改一个变量；假设必须可证伪；不得使用竞品爬取数据；没有基线就不下结论。

**验收：**30 例人工复核，诊断命中率 ≥70%；每条假设都能对应到具体数据。

## 6.3 FR-03 内容生成（P0）

**描述：**按 TaskOrder 生成 2–3 版文案、主图 brief 或图片、价格方案。

**输入：**产品资料、品牌规范、目标市场、价格带。

**输出：**候选方案包，每版含文案、素材、价格、预期。

**规则：**必须本地化（语言、单位、尺码、节日）；禁止绝对化用语；图片只用生成式素材、CC0 或自有素材。

**验收：**首次合规通过率 ≥60%；母语者盲评 ≥4/5；单 SKU 生成 ≤3 分钟。

## 6.4 FR-04 合规审查（P0）

**描述：**对每版做禁售、广告法、品牌词、版权四类检查，输出通过或不通过及违规项。

**输入：**候选方案、规则库。

**输出：**ReviewResult（verdict、violations、suggestions）。

**规则：**只看成品与规则，不看创作理由；误报率 ≤10%；漏报由人工抽检兜底。

**验收：**违规检出 ≥90%，误报 ≤10%；每一条违规都能指向具体规则与修改建议。

## 6.5 FR-05 审批与发布（P0）

**描述：**阈值内自动发布，超阈值转人工；发布带审批令牌，版本化，可一键回滚。

**输入：**PublishCommand、审批结果。

**输出：**listing 版本号、发布记录、审计链。

**规则：**降价 >10%、改类目、动品牌词、含人物或第三方素材，必须人审；令牌一次一用。

**验收：**发布成功率 ≥99%；回滚 <1 分钟；审计链完整可回放。

## 6.6 FR-06 实验与判定（P0）

**描述：**单变量实验，7 天或累计 1000 曝光，对照 3–5 个同类未改 SKU，判定保留、回滚或加推。

**输入：**实验记录、表现数据、对照组。

**输出：**判定结果、置信度、结论。

**规则：**不显著不采纳；失败实验也写结论；季节波动用对照组抵消。

**验收：**与人工复核一致率 ≥80%；每条判定都带样本量与对照组。

## 6.7 FR-07 记忆与 Playbook（P1）

**描述：**四层记忆；每次实验写结论；每周巩固成类目 Playbook。

**输入：**实验记录、人工反馈。

**输出：**记忆条目、Playbook、周报引用。

**规则：**单写者；人工结论覆盖模型结论；36 个月未复发的低权重记忆降权但不删除。

**验收：**跨会话召回率 ≥85%；Playbook 复用率 ≥60%。

## 6.8 FR-08 周报（P1）

**描述：**每周一生成：动了哪些 SKU、为什么、结果如何、下周计划。

**输入：**实验记录、记忆。

**输出：**周报页面与导出文件。

**规则：**必须带对照组与样本量；不许只报涨幅；结论要能直接指导下周动作。

**验收：**运营 5 分钟内能看懂并做出决策。

# 7. 数据与合规

## 7.1 数据源分级

表 7-1 数据源分级

| 数据源 | 例子 | 合法性 | 用法 |
| --- | --- | --- | --- |
| 自家店铺 | 曝光、点击、转化、退货、客服工单 | 绿：自己的数据 | 核心诊断依据，OAuth 接入 |
| 平台官方 API | Amazon SP-API、国际站开放平台 | 绿：授权 | 首选，签协议 |
| 付费第三方 | Jungle Scout、Keepa、SimilarWeb、海关数据 | 黄：看授权链 | 买服务，不自己爬 |
| 公开统计 | 海关总署、统计局、Google Trends | 绿：公开 | 做趋势，不做竞品明细 |

## 7.2 四条红线

- **平台规则：**不批量抓取商品页、评论、图片；不做绕过验证码或登录的技术措施。
- **著作权：**评论、图片、文案不复制；素材只用生成式素材、CC0 或自有。
- **广告法：**绝对化用语、虚假承诺、医疗功效表述，发布前拦截。
- **个人信息：**不采集买家昵称、头像、联系方式；跨境数据流动按项目所在地区评估。

## 7.3 架构闸门

每个数据源带 license 标签（own / authorized / public / scraper），scraper 默认禁用；数据入湖前打标，下游只能消费前三类；每次调用写审计日志。合规由代码保证，不靠文档里的承诺。

# 8. 记忆设计

## 8.1 四层记忆

表 8-1 四层记忆

| 记忆层 | 存什么 | 写 / 读策略 |
| --- | --- | --- |
| 商品档案 | SKU、成本、卖点、目标市场、合规状态 | 人工确认后写入；按 SKU 读 |
| 表现记忆 | 曝光、CTR、CVR、退货时间序列 | 每日同步，按窗口聚合 |
| 实验记忆 | 改了什么、结果如何、结论是什么 | 实验结束自动写，带样本量与置信度 |
| 类目 Playbook | 某类目或市场有效的做法 | 每周从 ≥3 条同类实验巩固 |

## 8.2 写入、召回与巩固

- **写入：**带来源、置信度、时间戳；人工结论权重高于模型结论。
- **召回：**按“相关 + 新近 + 重要”排序，不按时间倒序。
- **巩固：**每周把 ≥3 条同类实验合并成一条 Playbook，失败实验降权但不删除。
- **冲突：**新结论覆盖旧结论，旧记录标记 superseded_by，保留审计。
- **遗忘：**36 个月未复发的低权重记忆降权 0.5 倍，避免旧经验污染新判断。

## 8.3 记忆评测

评测里必须做两组对照：一组关掉记忆、一组开启记忆，跑同一批 50 个任务；再专门构造“误导历史”样本，看旧经验会不会把新故障带偏。记忆的价值要用消融证明，不能只讲“我们做了记忆”。

三组对照：关闭记忆、开启记忆；单 Agent、三 Agent；三 Agent、六 Agent。用同一批 50 个任务，比较任务完成率、决策准确率、成本与时延。

| 审计导出 | CSV 下载；UTF-8 BOM；防公式注入 |
| SQLite 多租户 | users / user_tenants / tenants 落库；console migrate 迁移 |
| 连接器 | selfhosted 已实现；Shopify / WooCommerce 明确报错 |
| HTTPS | --tls-cert/--tls-key；TLS 1.2+；HTTPS 下 HSTS |
| 审批 | approver 签发一次性令牌；operator 不能签发 |
| 发布 | 预览默认 dry-run；发布必须有效令牌；失败返回 409 |
| 页面 | 总览、店铺体检、本周动作、方案与审批、运行记录、记忆、系统管理；委托台与事实面板已于 Step 30 下线 |
| 离线 Demo | console serve --demo；快照预览，发布只读 |
| 当前账号 | 初始化时设置；管理面板可改密/停用/重置 |
