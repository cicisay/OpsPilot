# Step 1 — 项目骨架、领域模型、50 个 SKU、店铺模拟器

## 本步目标

先把三个 Agent 共用的“语言”和“试验场”搭起来：没有统一的领域模型，三个角色之间没法交接；没有可复现的环境，后面所有实验都无法归因。

## 交付物

| 文件 | 作用 |
|---|---|
| `src/ops_agent/models.py` | SKU、Performance、TaskOrder、Proposal、ReviewResult、Experiment、PlaybookEntry |
| `src/ops_agent/catalog.py` | 确定性生成 50 个 SKU（7 类目 × 3 市场） |
| `src/ops_agent/simulator.py` | 预期 CTR / CVR / 退货率、单变量改动、28 天模拟 |
| `src/ops_agent/cli.py` | `seed` / `summary` / `simulate` |
| `tests/` | 19 个单元测试 |
| `data/` | 生成物：`skus.json`、`performance.csv` |

## 关键决策

1. **先模型、后 Agent。** 三个 Agent 的交接全部依赖同一套对象；先定 schema，后面不用边写边改。
2. **用模拟器，不接真实平台。** 当前环境没有平台账号与浏览器，接真实店铺不可行；模拟器把“改动 → 指标”的关系显式写出来，反而更适合做消融。
3. **零第三方依赖。** 只用标准库，任何一台机器 `python run.py seed` 就能跑；后面接 LLM 时再引入 SDK。
4. **单变量改动。** `apply_change` 一次只动一个杠杆，保证后面实验能归因。

## 难点与解决

**难点 1：可复现性。**
用 `random.Random(seed)` 还不够——如果用 Python 内置 `hash()` 给每个 SKU 生成子种子，字符串哈希受 `PYTHONHASHSEED` 影响，每次进程启动都可能不同。改用 `zlib.crc32(sku_id.encode())`，跨进程稳定。

**难点 2：模拟数据不能自相矛盾。**
如果点击大于曝光、订单大于点击，后面的指标全是脏的。在 `Performance.__post_init__` 里直接把这些约束写死，让脏数据在构造时就报错，而不是等到统计时才发现。

**难点 3：机会分怎么设计。**
只按 CTR 差距排序，会优先优化“流量很小但差距很大”的 SKU，收益有限。机会分 = `(0.6 × CTR 差距 + 0.4 × CVR 差距) × 流量权重`，让“高流量、低转化”排在前面。

**难点 4：中文终端对齐。**
`ljust` 按字符数补齐，中文占两列，表格会歪。CLI 里用显示宽度（CJK 记 2）补齐。

## Bug 记录

**现象：** 第一次跑 `summary`，50 个 SKU 的机会分全是 `0.000`，排序等于没排。

**原因：** 机会分的基准取的是类目常数（`CATEGORY_PROFILES[category]["ctr"]`），但生成样本的预期指标普遍高于这个常数——图片、标题、价格几个乘子叠起来均值在 1.3 左右，所以没有任何 SKU 低于基准，`gap` 全被截成 0。

**修复：** 基准改成“同批 SKU 的类目中位数”，先由 `category_benchmarks()` 算出每个类目的 CTR/CVR 中位数，再算差距；同时补了一条回归测试 `test_some_skus_fall_below_benchmark`，防止再出现“全员达标”。

## 验收结果

- `python -m unittest discover -s tests -v`：19 个测试全部通过。
- `python run.py seed`：生成 50 个 SKU、1400 行表现数据。
- `python run.py summary`：输出按机会分排序的 SKU，前五名分数在 0.21–0.27。
- `python run.py simulate --sku SKU-1003 --change scene_image`：CTR 预期 +10.3%。

## 设计问答

**Q1：为什么先做模拟器，而不是直接接平台 API？**
A：接 API 需要账号、授权和真实流量，本地无法稳定复现；而且平台数据是“黑盒”，改动和结果之间混杂了季节、广告、竞品。模拟器把因果链显式写出来，适合验证 Agent 的决策与归因逻辑。接真实 API 是部署阶段的事，不是开发阶段的事。

**Q2：数据是假的，结论可信吗？**
A：这个阶段验证的是“机制”不是“效果”：Agent 能不能选对 SKU、能不能做单变量实验、能不能在证据不足时停手。真实效果要等接入客户店铺后，用同样的评测口径重跑。文档里明确标注了模拟数据，不承诺 GMV。

**Q3：机会分为什么这么设计？会不会只优化大流量 SKU？**
A：会偏向大流量，这是有意的——同样提升 1 个百分点，大流量 SKU 的绝对收益更高。但如果只按流量排，会忽略“差距极大”的长尾；所以用 0.6/0.4 的差距权重和 `log1p` 流量权重，让两者都进得来。后面会用人工评审校准排序。

**Q4：为什么用 dataclass 不用 Pydantic？**
A：这一层只做结构校验，没有序列化、别名、嵌套模型的复杂需求；标准库 dataclass 足够，零依赖也让测试更快。等接 LLM 工具调用、需要 JSON Schema 时，再在工具层引入 Pydantic，不冲突。

**Q5：单变量改动怎么保证真的只改一个？**
A：`apply_change` 是唯一入口，只接受五种枚举改动，每种只改一个字段；测试里对每种改动断言“目标指标变化、其他不变”。后面 Agent 也只能通过这个函数改。

**Q6：这套模型和真实店铺差距在哪？**
A：三点——真实 CTR 受广告、季节、竞品影响更大；真实转化受评价和物流时效影响更非线性；真实退货有品类结构性差异。模拟器是有意简化的，用来测流程，不用来预测。
