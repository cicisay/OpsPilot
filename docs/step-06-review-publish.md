# Step 5 — 合规审查 + 发布编排

> 2026-10-30 更新：`--approve` 已移除，改为 `approve issue` + `--approval-token`；测试数已增至 106。以 `step-07-p0-hardening.md` 为准。

## 本步目标

把内容工坊的方案变成“可安全上线”的动作：

- 合规独立成角色，只拿成品和规则，可否决；
- 发布默认只 dry-run 预览，显式批准才写入；
- 写入带幂等键，失败有补偿回滚；
- 全程可审计。

## 关键决策

1. **合规是独立角色，不是工坊的自检。**
   `ComplianceReviewer.review(variant, product)` 只接收成品和商品事实，不接收 TaskOrder 的创作理由；上下文隔离，避免“被说服”。
2. **发布默认 dry-run。**
   `publish run` 不加 `--approve` 只预览：调用连接器的 `?dryRun=true`，拿服务端 diff，不写库。
3. **超过 10% 的改价必须显式批准。**
   `price_change_pct > 10%` 时返回 `approval_required`，即使调用方传了 `--approve`，也要先过合规。
4. **写入用幂等键。**
   商品内容用 `pub-{productId}-{variantKey}-p`，SKU 价格用 `...-v`；网络重试不会重复发布。
5. **部分失败要补偿。**
   商品内容先写，SKU 价格后写；如果价格写失败，自动 `rollback` 商品到刚生成的版本，避免“标题变了价格没变”。
6. **审查不只看词库。**
   还检查标题长度、卖点数量/单条长度、描述长度、价格是否低于毛利底线。

## 难点与解决

**难点 1：角色隔离。**
如果合规能看到工坊的“这个卖点很抓人”的理由，它就会开始找理由放行。解决：`review()` 的入参只有 variant + product，TaskOrder 不传；测试也按这个边界写。

**难点 2：发布顺序与补偿。**
先改内容再改价格，任何一步失败都会留下半成品。解决：记下商品版本号；价格失败时调用 `rollback` 回滚商品版本，并返回 `failed`。

**难点 3：审批阈值边界。**
任务带本身是 ±10%，第一版价格正好 -10%，`> 10%` 不触发审批。这是有意的：10% 以内是自动区，超过才要人。测试用 19.4% 验证触发。

**难点 4：幂等键的字符与长度。**
连接器要求 8–128 字符 `[A-Za-z0-9_.:-]`。商品 ID 是 cuid，variant key 里有 `-`，拼出来后截断到 120 字符，仍在规则内。

**难点 5：不能拿真实店铺做写入测试。**
验收只做 dry-run；真实写入路径用假站点单测覆盖（成功、审批拦截、合规拦截、价格失败补偿）。这样不会动用户的数据。

## Bug 记录

**Bug 1：审查测试的价格没有真的低于底线。**
测试用价格 500、成本 400，毛利底线 477，500 其实高于底线，断言却期望失败。修复：改成 450，真正低于 477。

**Bug 2（设计限制，不是代码 bug）：价格检查只按最低价 SKU 的成本。**
如果方案针对的是第二个 SKU，成本可能不同。当前只发最低价 SKU，所以先用它的成本；多 SKU 发布时要按目标 SKU 取成本。

## 验收结果

- `python -m unittest discover -s tests -q`：82 个测试通过（新增 11 个）。
- `python run.py review run --offline --limit 3`：9 个版本，9/9 通过。
- `python run.py publish run --limit 1`：
  - 状态 `已预览`，价格变动 10.0%，不触发审批；
  - `product_diff` 含 `titleEn / descEn / bulletsEn`，`variant_diff` 含 `priceCents`；
  - 没有写入站点。
- 假站点单测覆盖：
  - 19.4% 改价 → `approval_required`；
  - 显式批准 → 两次写入（商品 + SKU），带幂等键；
  - 合规失败 → `blocked`，不写入；
  - 价格写入失败 → `failed`，商品已回滚。

## 设计问答

**Q1：合规为什么要独立成角色？**
A：工坊的目标是“写得好看”，合规的目标是“别踩线”，两个目标天然冲突。放在同一个上下文里，模型会自我说服；独立角色只拿成品和规则，才能真的否决。

**Q2：发布为什么默认 dry-run？**
A：发布是不可逆动作里最贵的一步。默认 dry-run 让商家先看 diff，确认后再写；`--approve` 是显式确认，不是默认行为。

**Q3：10% 的阈值怎么处理？**
A：`> 10%` 触发人工审批；正好 10% 不触发。任务带本身就是 ±10%，所以大部分自动方案落在自动区；超出才升级。

**Q4：幂等键怎么设计？**
A：商品内容 `pub-{productId}-{variantKey}-p`，SKU 价格 `...-v`；同一次发布重试会命中同一个键，站点直接返回第一次的结果，不会重复生成版本。

**Q5：部分失败怎么补偿？**
A：先写商品内容，拿到 versionId；价格写失败就 `rollback` 到该版本，商品内容和价格一起回到发布前。返回 `failed`，不假装成功。

**Q6：怎么保证不误写真实店铺？**
A：验收只跑 dry-run；真实写入测试用假站点。`--approve` 必须显式传，且先过合规；生产环境还要把“人工批准”换成运营台里的真实审批动作。

## 已知限制

1. `--approve` 是 CLI 显式确认，不是运营台的真实审批流；UI 接入后要换成审批令牌。
2. 合规词库固定 `US`；DE/UK 差异未接。
3. 只发最低价 SKU；多 SKU 方案需要按目标 SKU 取成本和变体 ID。
4. 真实站点验收只做 dry-run，没有实际发布；写入路径靠假站点覆盖。
5. 没有批量发布和并发控制；多商品发布要排队并加锁。
